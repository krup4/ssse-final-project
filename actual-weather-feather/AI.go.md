# О проекте

Данный репозиторий содержит микросервис **Actual Weather Service**.

Это один из сервисов дипломного проекта по построению распределённой платформы анализа точности прогнозов погоды.

Общая идея системы:

1. Один сервис получает прогнозы погоды.
2. Данный сервис получает фактическую погоду.
3. Отдельный сервис сравнивает прогноз с фактом.
4. Далее аналитический сервис строит графики и вычисляет ошибки прогнозов.

Данный репозиторий отвечает **только за получение фактической погоды**.

---

# Главная ответственность сервиса

Сервис должен:

- получать список активных станций;
- каждый полный час получать фактическую погоду;
- использовать Open-Meteo API;
- валидировать ответ;
- сохранять данные в PostgreSQL;
- публиковать события в Kafka;
- собирать метрики;
- логировать ошибки.

Сервис НЕ должен:

- считать ошибки прогнозов;
- хранить прогнозы;
- выполнять аналитические запросы;
- обслуживать пользователей;
- строить графики.

Не нарушать принцип Single Responsibility.

Все станции находятся в PostgreSQL.

Stations

id

name

latitude

longitude

region

active

Получение погоды должно происходить для всех активных станций.

# Расписание

Получение данных происходит автоматически.

Интервал:

каждый полный час.

Например:

00:00

01:00

02:00

...

23:00

Если сервис стартовал в 15:17

необходимо дождаться 16:00.

Нельзя получать данные каждые 60 минут относительно момента запуска.

# Архитектура

Использовать Clean Architecture.

Разделение по слоям обязательно.

```
cmd/

internal/

    api/

    service/

    repository/

    models/

    database/

    kafka/

    client/

    monitoring/

    middleware/

configs/

migrations/
```

Нельзя смешивать слои.

Repository не должен знать про HTTP.

Client не должен знать про PostgreSQL.

Service не должен выполнять SQL.

# Конкурентность

Каждая станция должна обрабатываться независимо.

Использовать goroutines.

При необходимости использовать WaitGroup.

Все конкурентные операции должны корректно завершаться через context cancellation.

Не допускать race conditions.

# Самое важное

Не пытаться реализовать всё в одном пакете.

Не нарушать Clean Architecture.

Любой новый код должен легко тестироваться.

Любая бизнес-логика должна находиться только в Service.

Repository работает только с БД.

Client работает только с Open-Meteo.

API ничего не знает о реализации.

Все зависимости должны внедряться через конструкторы.

При возникновении неоднозначностей выбирать наиболее простое, расширяемое и production-подобное решение.
